## 第二部分：可靠性增强（6 项）

### 建议 2.1：LLM Service 引入重试 + 熔断 + 降级

**现状问题**：`LLMService.ts` 每次请求失败后直接返回错误，无重试机制，无熔断保护。当某个 Provider 持续不可用时，会反复等待超时，阻塞用户交互。

**具体建议**：

```
请求流程（改进后）：

用户请求 → Circuit Breaker → [Open?] → 快速失败 + Provider 降级
               ↓ [Closed]
          Retry Policy (指数退避, 最多 3 次)
               ↓
          Provider A ──失败──→ Provider B ──失败──→ Provider C
               ↓ 成功
          返回结果 + 更新熔断状态
```

| 配置项 | 推荐值 |
|--------|--------|
| 重试次数 | 3 次 |
| 退避策略 | 指数退避：1s → 2s → 4s |
| 熔断阈值 | 5 次连续失败后打开 |
| 熔断恢复 | 30s 后半开探测 |
| 降级策略 | 按优先级切换至下一可用 Provider |

**关键实现点**：
- 对 `429 Rate Limit` 响应实施更长退避（`Retry-After` 头部感知）
- 对 `401/403` 认证错误不重试（直接跳转配置）
- 对 `timeout` 错误重试，对 `CORS` 错误不重试

---

### 建议 2.2：Zustand Persist 中间件增加容错层

**现状问题**：所有使用 `persist` 中间件的 Store 在 `localStorage/IndexedDB` 满或损坏时会静默失败或抛出未捕获异常，导致整个应用崩溃。

**具体建议**：

```
持久化流程（改进后）：

Store 变更 → persist.write() → try { serialize + write }
                                    ↓ 失败
                                 catch → QuotaExceededError?
                                           ↓ 是
                                         通知用户 + 清理旧数据
                                           ↓ 否
                                         降级为内存模式 + 上报错误
```

- 在 `persist` 的 `storage` 参数中封装自定义 Storage 实现，对 `setItem` 做完整 `try-catch`
- 对 `QuotaExceededError` 触发用户通知，提示清理旧项目数据
- 对 `DataError`/`InvalidStateError`（存储损坏）自动清空损坏数据并重建

---

### 建议 2.3：IndexedDB 增加损坏检测与恢复

**现状问题**：`IndexedDBAdapter` 没有数据库完整性校验，一旦数据库损坏，所有读写操作静默失败。

**具体建议**：
- 启动时执行 `IDBDatabase` 健康检查（读写测试记录）
- 检测到损坏时自动执行 `idb.deleteDatabase()` 重建
- 对关键数据维护 `localStorage` 备份（仅元数据和设置，不含文件内容）
- 所有写操作增加 `QuotaExceededError` 捕获并通知用户

---

### 建议 2.4：AI 流式响应增加取消与资源清理

**现状问题**：SSE 流式响应在组件卸载时未中断，造成网络请求泄漏和 `state` 更新到已卸载组件。

**具体建议**：
- 所有 AI 请求持有 `AbortController`，在 `useEffect` 清理函数中调用 `abort()`
- 聊天面板增加"停止生成"按钮，调用 `AbortController.abort()`
- 大响应（>10000 token）实施缓冲写入，避免逐 token 触发重渲染
- 对话历史超过阈值时实施窗口裁剪，保留最近 N 轮

---

### 建议 2.5：插件系统增加健康检查与自动恢复

**现状问题**：插件崩溃后进入 `error` 状态，不会自动恢复，需手动重启。

**具体建议**：
- 插件激活后启动心跳检测（每 30s），检测无响应自动重启
- 连续崩溃 3 次后标记为 `unstable`，降级为安全模式（禁用事件处理）
- 提供 `PluginHealthMonitor` 面板展示所有插件状态
- 插件间依赖关系图，某插件崩溃时通知下游插件

---

### 建议 2.6：全局错误边界完善

**现状问题**：`ErrorReportingService` 捕获了全局错误，但缺少 React Error Boundary 组件级隔离。

**具体建议**：
- 为每个面板包裹独立的 `ErrorBoundary`，单面板崩溃不影响全局
- Monaco 编辑器单独 ErrorBoundary，编辑器异常时降级为只读模式
- 插件渲染使用 ErrorBoundary，插件 UI 崩溃时显示错误占位符
- Error Boundary 捕获的错误统一上报到 `ErrorReportingService`

## 第三部分：性能优化（7 项）

### 建议 3.1：PanelManager 渲染优化

**现状问题**：`PanelManager` 使用 `JSON.parse(JSON.stringify())` 进行深拷贝，任何面板状态变化导致整棵布局树重新渲染。

**具体建议**：

| 问题 | 优化方案 |
|------|----------|
| 深拷贝性能差 | 使用结构化共享（`structural sharing`）替代深拷贝 |
| 全局重渲染 | 每个面板使用 `React.memo` + 精确 `props` 比对 |
| 拖拽频繁 `setState` | 使用 `requestAnimationFrame` 节流 + `CSS transform` 替代状态驱动 |
| 布局计算在主线程 | 复杂布局计算移至 `Web Worker` |

- Resize 拖拽使用 `ref` 直接操作 DOM style，仅在 `mouseup` 时同步到 `state`
- 面板内容区域使用 `React.lazy` 按需加载，不可见面板不渲染 DOM

---

### 建议 3.2：Store Selector 规范化

**现状问题**：部分组件直接解构整个 `Store` 而非使用 `Selector`，导致无关状态变更触发组件重渲染。

**具体建议**：

```
// 反模式（当前）
const { files, activeFile, tabs, gitStatus } = useFileStoreZustand();

// 正确模式（推荐）
const files = useFileStoreZustand(s => s.fileContents);
const activeFile = useFileStoreZustand(s => s.activeFile);
```

- 全量审查所有 Store 消费组件，确保使用细粒度 `Selector`
- 对计算派生值（如 `fileTree`）使用 `useMemo` + 浅比较
- 引入 `useShallow` `Selector` 处理多值订阅

---

### 建议 3.3：Monaco Editor 实例生命周期管理

**现状问题**：Monaco 实例的事件监听器（滚动同步、光标追踪）在组件卸载时未完整释放。

**具体建议**：
- 统一在 `useEffect` 返回的清理函数中 `dispose()` 所有 `disposable`
- 编辑器实例使用 `useRef` 持有，避免重复创建
- 主题切换时使用 `editor.setTheme()` 而非重新挂载组件
- Worker 池化管理，多个编辑器实例共享 `Worker`

---

### 建议 3.4：虚拟文件树优化

**现状问题**：`flattenTree` 在任何文件变更时重新计算整棵树的扁平化结果。

**具体建议**：
- `flattenTree` 结果使用 `useMemo` 缓存，仅在 `fileContents/expansionState` 变更时重算
- 使用增量更新：新增/删除文件时仅更新受影响分支
- 大型项目（>1000 文件）启用虚拟化渲染，仅渲染可视区域
- 搜索时先过滤再扁平化，避免全量计算

---

### 建议 3.5：i18n 按需加载

**现状问题**：所有语言的翻译对象在启动时全量加载。

**具体建议**：
- 使用动态 `import()` 按语言加载翻译文件：`const dict = await import('./zh-CN.json')`
- 切换语言时异步加载，加载期间保持当前语言
- 翻译查找表使用 `Map` 替代嵌套对象遍历（O(1) vs O(n)）
- 支持按模块拆分翻译（`editor.json`、`terminal.json`、`ai.json`）

---

### 建议 3.6：Bundle 分包策略

**具体建议**：

```
初始包（<200KB gzip）：
├── React + React-DOM
├── Zustand
├── Router
└── 核心布局组件

按需加载：
├── Monaco Editor（~2MB）— 首次打开代码文件时加载
├── TipTap Editor（~300KB）— 首次打开文档时加载
├── Sandpack（~500KB）— 首次使用预览时加载
├── Y.js + Provider（~200KB）— 首次开启协作时加载
└── CryptoService（~50KB）— 首次需要加密时加载
```

- `Vite` 的 `import()` + `React.lazy()` 实现自动代码分割
- Monaco Editor 使用 `@monaco-editor/loader` 的 `configure` 指定 CDN 路径

---

### 建议 3.7：SSE Token 渲染节流

**现状问题**：AI 流式响应逐 `token` 触发 `setState`，高频更新导致大量重渲染。

**具体建议**：
- 使用 `requestAnimationFrame` 或 50ms 间隔批量缓冲 `token`
- 渲染层使用 `useRef` 累积文本，`useState` 仅控制渲染触发频率
- 代码块检测完成后才触发语法高亮（避免中间状态闪烁）

```
{
  "version": 1,
  "name": "项目名称",
  "panels": { 布局配置 },
  "openFiles": ["src/App.tsx", "README.md"],
  "terminalSessions": [{ "cwd": "/src", "history": [] }],
  "aiContext": { "model": "glm-4", "systemPrompt": "..." }
}
```

- 支持导出/导入工作区配置
- 提供预设模板：React 开发、Vue 开发、Node.js 后端、全栈开发
- 最近工作区列表（最近 10 个）

### 建议 5.8：通知系统真实化

**现状**：通知 `UI` 存在但为静态数据。

**建议**：
- 实现统一的 `NotificationService`：

```
通知源：
├── AIService — 生成完成、错误、重试

通知类型：

├── Badge（面板图标角标数字）
└── Sound（可选提示音）
```

## 第六部分：安全加固（3 项）

### 建议 6.1：API Key 安全增强

**现状**：`APIKeySettingsUI.tsx` 存在 24 处 `any` 类型，`API Key` 存储安全存疑。

**具体建议**：
- `API Key` 存储：使用 `CryptoService` 加密后存储，禁止明文存储
- `API Key` 输入：始终使用 `type="password"` + 显示/隐藏切换
- `API Key` 展示：仅显示后 4 位（`sk-****1234`）
- `API Key` 传输：通过 `Bridge` 层加密传输，不暴露到前端全局
- 引入 `API Key` 轮换提醒（配置过期时间）

---

### 建议 6.2：插件权限精细化

**现状**：插件 `API` 暴露较宽泛，缺少细粒度权限声明。

**建议的权限模型**：

```
插件 manifest.json：
{
  "permissions": [
    "editor:read",          // 读取编辑器内容
    "editor:write",         // 修改编辑器内容
    "files:read",           // 读取文件列表
    "files:write",          // 创建/修改文件
    "ai:access",            // 调用 AI 服务
    "network:fetch",        // 发起网络请求
    "clipboard:read",       // 读取剪贴板
    "storage:local",        // 本地存储
    "notifications",        // 发送通知
    "commands"              // 注册命令
  ]
}
```

- 安装时展示权限列表，用户确认后才激活
- 运行时动态检查权限，越权操作抛出异常
- 网络请求限制域名白名单

---

### 建议 6.3：内容安全策略 (CSP)

**建议**：
- 配置 `Content-Security-Policy` HTTP 头
- 限制 `eval()` 使用（Monaco 需要 `eval` 的场景使用 `nonce` 放行）
- 插件 `iframe` 沙箱化渲染（`sandbox` 属性）
- 外部资源加载仅允许白名单域名

---

## 第七部分：架构演进建议（3 项）

### 建议 7.1：服务层抽象化（后端无关）

**现状**：部分服务直接在前端实现（如 `LLM` 调用、文件操作），难以支持多种后端。

**建议**：

```
                    ┌─────────────────────┐
                    │   Service Interface  │
                    │  (抽象接口层)         │
                    ├─────────────────────┤
                    │ FileService         │
                    │ GitService          │
                    │ TerminalService     │
                    │ DebugService        │
                    │ AIService           │
                    └───────┬─────────────┘
                            │
              ┌─────────────┼─────────────┐
              ↓             ↓             ↓
     ┌────────────┐ ┌────────────┐ ┌────────────┐
     │ WebAdapter │ │ TauriAdapter│ │ RemoteAdapter│
     │ (浏览器)    │ │ (桌面端)    │ │ (远程服务端)  │
     │ IndexedDB  │ │ 本地文件系统 │ │ WebSocket   │
     │ WebWorker  │ │ portable-pty│ │ DAP Server  │
     └────────────┘ └────────────┘ └────────────┘
```

- 所有后端依赖通过 `Bridge` 层接口访问
- 当前已有的 `bridge/host.ts` 扩展为完整的服务抽象层
- 新增功能面向接口开发，不直接依赖具体实现

---

### 建议 7.2：事件系统类型化

**现状**：`WorkflowEventBus` 的 50+ 事件类型为字符串，无编译时类型检查。

**建议**：
- 使用 TypeScript 字面量类型定义事件名：

```
type WorkflowEvents = {
  'design:input': { content: string; source: string };
  'code:generated': { fileId: string; code: string };
  'ai:token': { token: string; requestId: string };
  'collab:cursor': { userId: string; position: Position };
  // ... 50+ events
};
```

- `EventBus` 泛型化：`emit<K extends keyof WorkflowEvents>(event: K, data: WorkflowEvents[K])`
- 编译时捕获事件名拼写错误和数据类型不匹配

---

### 建议 7.3：状态管理收敛

**现状**：17+ 独立 Store，Store 间偶尔存在隐式依赖。

**建议**：
- 将紧密相关的 Store 合并（如 `ThemeStore` + `CustomThemeStore` → 统一 `ThemeStore`）
- Store 间通信通过事件总线，禁止直接引用其他 Store
- 引入 Store 依赖关系图，可视化 Store 间交互
- 长期考虑：核心 Store 合并为单一 Root Store，通过 `slice` 机制分离

## 总结

本报告基于对 IDE 系统全部源码的逐模块审计，识别出 **24 项具体改进建议**，分布在 6 大领域：

| 领域 | 建议数 | 核心收益 |
|------|--------|----------|
| 可靠性 | 6 项 | 从"能用"到"可靠"，消除崩溃和数据丢失风险 |
| 性能 | 7 项 | 面板/编辑器/流式渲染全链路优化，体感流畅度大幅提升 |
| 代码质量 | 5 项 | 类型安全 + 测试覆盖 + 工具链，降低长期维护成本 |
| 功能完善 | 8 项 | 终端/Git/搜索/调试/协作从 UI 示例升级为真实能力 |
| 安全加固 | 3 项 | API Key 保护、插件权限、CSP 策略三重防线 |
| 架构演进 | 3 项 | 后端无关化 + 类型化事件 + 状态收敛，支撑长期扩展 |

建议按照 Phase 1→4 的路线图分阶段实施，每个 Phase 内的条目可并行推进。Phase 1 聚焦稳定性和安全基础，是后续所有工作的前提。
